# Bahn Ops Controller

**What this is.** Bahn moves used cars with freelance drivers, and every
delivery is a chain of people who do not work for Bahn: the seller holding the
car, the driver, the ferry line, whoever signs at the other end. When one link
breaks, a person in operations rebuilds the whole chain from phone logs.

This is the room where the chain is visible, and one agent that does the first
link's work by itself.

**What the agent does.** It reads the open alerts in Bahn's dataset, pulls the
order, notes, messages, documents, reservations and driver rows attached to
each, and writes one proposal per alert. Every proposal carries the ids it
relied on, plus two classifications per fact: who said it (app, site, driver,
ferry, document, billing, customer) and what state it is in (stale, reported,
quoted, missing, disputed, conflicting). When the evidence does not support an
action it stops and says why instead of proposing.

**Why the classifications matter.** Bahn's own operations context warns that a
quote can be mistaken for a booking, or a driver message for a fresh location.
The board keeps those distinctions visible, so a person checks the agent's
reasoning instead of rebuilding it.

**What the board shows.** Only the alerts that need a person. Each card carries
the reason it surfaced, the agent's proposal, the rationale, the evidence ids,
the source and state chips, and where the agent declined a stop reason in place
of the Accept button. Above the queue, one line accounts for the alerts that are
hidden: how many were resolved, how many acknowledged, and how many have no
reason recorded in Bahn's own data.

**The decision loop.** Accept or Change writes a decision to
bahn_ops/decisions.jsonl with a timestamp and the approved command. Reload the
page and the decision is still there. Asking and looking up need no permission;
changing anything waits for a person.

**The model.** The proposal loop calls a language model per alert. With no key
it runs a deterministic path and records why in model_error; with a key each row
records source: model. The fallback exists so the control room is never empty,
and it records its own reason.

Three entry points. Each runs on its own; none requires another.

## 1. Control room (Node, no dependencies)

 node board/server.cjs

Serves http://127.0.0.1:4317 — only the orders that need a person, each with
the reason it surfaced, the agent proposal, the rationale, and the ids the
proposal relied on.

Reads bahn_ops/ours.jsonl when that file exists, and falls back to the
shipped board/dataset/data/agent_proposals.jsonl when it does not.

## 2. Agent (Python 3, stdlib only)

 python3 bahn_ops/agent.py

Reads the open alerts from board/dataset/data, writes one proposal per alert
to bahn_ops/ours.jsonl. Safe to rerun: alerts already present in that file
are skipped.

No model key means the deterministic path runs and each row records the
reason in model_error. A key means the model writes the proposal and each
row records source as model.

## 3. Ops API (FastAPI)

 python3 -m venv .venv
 .venv/bin/python -m pip install -r requirements.txt
 .venv/bin/python -m uvicorn app.main:app --port 8000

Health: http://127.0.0.1:8000/health

## Config

Copy .env.example to .env and fill locally. Never commit .env.

 BAHN_MODEL_API_KEY=
 BAHN_MODEL_BASE_URL=
 BAHN_MODEL_NAME=

Blank settings run the deterministic path.

## What is in here

- board/server.cjs — the control room.
- board/dataset/ — Bahn's synthetic dataset, 50 jsonl files.
- bahn_ops/agent.py — the proposal loop.
- bahn_ops/ours.jsonl — generated by the agent. Not tracked.
- bahn_ops/controller.py — first build, deterministic order parsing, pricing,
 driver assignment. Kept as history, not the submission.
- app/main.py — FastAPI shell.
- PROCESS.md — how this was built with AI, written during the build.

## Model configuration

The agent calls any OpenAI-compatible chat endpoint. Nothing about the
provider is hardcoded; `bahn_ops/agent.py` reads three values and builds the
request URL from them.

    BAHN_MODEL_API_KEY=your key
    BAHN_MODEL_BASE_URL=https://api.anyapi.ai/v1
    BAHN_MODEL_NAME=nvidia/nemotron-3.5-lightning:free

Any of these work; `.env.example` lists all four with the exact strings:

- **AnyAPI**, `https://api.anyapi.ai/v1`, what this build uses.
- **OpenRouter**, `https://openrouter.ai/api/v1`, many free models.
- **OpenAI**, `https://api.openai.com/v1`.
- **A local server** on `http://127.0.0.1:8080/v1` — llama.cpp, vLLM,
  LM Studio, Ollama. The brief allows local models and nothing here
  prevents one.

If a value is already set in your shell, it wins over `.env`, because the
loader uses `os.environ.setdefault`. Set `BAHN_MODEL_NAME` in a shell to try
a model without editing a file.

Blank settings mean the deterministic path runs. That path is not a
degraded mode — it is the fallback the agent writes when no model answers,
and every row it produces records why in `model_error`. A clone with no key
produces twelve proposals, nine from the deterministic path and three
refusals, and the board prints the reason on every card.

The parser reads `choices[0].message.content` first and falls back to
`reasoning_content`. That matters for reasoning models, which spend tokens
thinking before answering and return null content when they are truncated.
This build ships `max_tokens: 6000` for that reason; at 600 the model used
its whole budget thinking and never answered.

## What a fresh clone shows

A fresh clone has no `bahn_ops/ours.jsonl`, so the board opens with the shipped
examples from `board/dataset/data/agent_proposals.jsonl` alongside the 12 open
alerts. Five of those alerts carry a shipped proposal. The other seven show
**"The agent has not looked at this case yet — Run agent on this case."** Click
the button and `case_chat.run_case` runs on that one alert, writes the result
to `bahn_ops/ours.jsonl`, and the card fills in. That is the intended first-run
experience: the agent is not a page of stale output, it is a button a person
presses.
